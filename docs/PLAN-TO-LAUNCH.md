### 8.1 Резервные копии и проверка восстановления
Зачем: на своём сервере сломанный диск или ошибка = потеря заказов, клиентов, остатков, ключей.
- **Что копируем**: база (`pg_dump -Fc`), папка фото `MEDIA_DIR`, **ключ шифрования** (`SECRETS_KEY` / `.data/secrets.key` — без него ключи
  «Интеграций» в копии не расшифровать). Поисковый индекс не копируем — пересобирается `pnpm search:reindex`. Фиды (`.data/feeds`) не нужны.
- **Когда**: каждый день в 03:30 из `runJobs` (как сводка 21:00), хранить 14 ежедневных + 8 еженедельных, старые удалять. Папка — `BACKUP_DIR`
  (новая переменная в `.env.example`; пусто — `.data/backups`). Фото — не целиком каждый день, а новые файлы (копия папки с пропуском уже скопированных).
- **Вторая копия вне сервера** (на случай, если умер весь сервер): выгрузка в S3-совместимое хранилище — поле в `INTEGRATIONS` («Резервные копии: адрес,
  ключ, корзина»); без ключа — только локально + предупреждение в «Резервных копиях». Какое хранилище — вопрос владельцу (Д-строка), допущение: любое S3-совместимое.
- **Проверка восстановления**: раз в неделю автоматически восстановить последнюю копию во временную базу `handyman_restore_check`, сверить число строк
  в главных таблицах (Product, Order, Client, StockMove …), удалить временную базу. Не получилось — тревога владельцу в Telegram (механизм тревог 4.8).
- **Админка «Резервные копии»** (`/admin/backups`, только владелец — `requireOwner()`): список копий (дата, размер, проверена ли), «Сделать копию сейчас»,
  «Скачать» (файл базы — только владельцу, запись в `AuditLog`), состояние второй копии. Модуль — `packages/db/src/backups.ts`, чистая логика
  (какие копии хранить, имена файлов) — `packages/core/src/backups.ts` с тестами.
- **Восстановление вручную**: `pnpm backup:restore <файл>` + раздел в `docs/BACKUPS.md` (пошагово для владельца и для сервера).
- Откуда `pg_dump`: на сервере — в боевом образе (8.4 ставит `postgresql16-client`); на ПК владельца — через `docker exec handyman-next-postgres-1 pg_dump`
  (путь к docker — как в `scripts/update-site.ps1`). Выбор способа — одна функция в `backups.ts`.
- Тесты: интеграционный — копия `handyman_test` → восстановление во временную базу → совпадают строки; core — правило хранения 14/8.

- **Админка «Ошибки»** (`/admin/errors`; новое право `errors.view` — у владельца и администратора; порядок добавления права — по правилу 2 в `CLAUDE.md`):
  группы одинаковых ошибок со счётчиком, последний раз, «Закрыть». Хранить 30 дней (чистка в `runJobs`). Добавить `error.tsx` для админки.
- **Тревога**: новая группа ошибок или всплеск (≥ 20 за 10 минут) — сообщение владельцу в Telegram не чаще раза в час на группу.
- **Здоровье**: `/api/health` — база, поиск, когда последний раз отработал `runJobs`, место на диске, последняя удачная копия (8.1). Отвечает кратко
  «ok/ошибка» без подробностей наружу (подробности — только с ключом). Для внешнего бесплатного сторожа (например, UptimeRobot) — сторож
  подключается на сервере (8.5). Блок «Здоровье сайта» на дашборде `/admin`.
- Тесты: группировка по отпечатку, маскирование, лимит тревог (core); запись/чистка (db).

### 8.3 Защита: спам-заказы, вход в админку, безопасные настройки
Зачем: чтобы боты не завалили менеджера фальшивыми заказами и никто не подобрал пароль.
- **Лимиты в базе, а не в памяти** (сейчас `tooMany()` в `app/[lang]/cart-actions.ts` — в памяти, сбрасывается при перезапуске): общий модуль
  `packages/db/src/rate-limit.ts` (таблица или Redis — выбрать одно; Redis уже в compose). Применить ко всем публичным формам: заказ, «1 клік»,
  «Передзвоніть мені», отзывы и вопросы, «Повідомити», коды входа (SMS/Telegram), `/api/client-error`.
- **Ловушки для ботов**: скрытое поле `website` (уже есть в заказе) — во всех формах из списка выше; «слишком быстро заполнено» (меньше 3 секунд).
- **Повторный заказ**: тот же телефон + та же корзина за 10 минут → не создавать второй, показать первый.
- **Чёрный список** (`/admin/clients` → «Заблокировать»; телефон/адрес): заказ принимается, но помечается «подозрительный» и не уходит в KeyCRM
  автоматически (покупателю не сообщаем, что он в списке). Допущение → строка в `docs/QUESTIONS-TO-OWNER.md`.
- **Вход в админку**: лимит попыток пароля и кода (5 за 15 минут на логин и на адрес), тревога владельцу при переборе; проверить `db/src/staff.ts`.
- **Заголовки безопасности** (`next.config.ts` → `headers()`): HSTS (только в production), `X-Content-Type-Options`, `Referrer-Policy`,
  запрет встраивания сайта в чужие страницы, **кроме Telegram** (Mini App: `frame-ancestors https://web.telegram.org …`); куки `Secure` в production.
- **Проверка перед запуском** (`/admin/launch-check`, только владелец): список «готово / не готово» — сменён ли `ADMIN_TOKEN` и пароль `owner`, задан
  `SECRETS_KEY`, ключ поиска не `change-me`, `PUBLIC_URL` https, у владельца включён код из приложения (4.7), есть свежая копия (8.1), нет временных
  входов (`HM_TMP_LOGIN`, `app/api/tmp-claude-login`), ключи в «Интеграциях» проверены. В production при опасных значениях (`change-me`) —
  сайт пишет предупреждение в журнал ошибок (8.2), а не падает.
- `pnpm audit --prod` — разобрать высокие уязвимости (обновить без смены мажорной версии; иначе — строка в CHANGELOG).
- Тесты: лимиты, ловушки, повторный заказ, блокировка (db); e2e — форма заказа не ломается у обычного покупателя.

### 8.4 Сборка для сервера (Docker) и обновление на сервере
Зачем: сейчас сайт работает только на ПК владельца; для хостинга нужна готовая сборка, которая запускается одной командой.
- `apps/web/next.config.ts`: `output: "standalone"`; **`apps/web/Dockerfile`** (многоступенчатый: установка → `prisma generate` → `next build` →
  маленький образ с `node server.js`, `postgresql16-client` для копий 8.1, запуск не от root). Бот и фоновые задачи уже внутри сайта (`lib/worker.ts`),
  отдельный контейнер `apps/bot` на сервере не нужен.
- **`docker-compose.prod.yml`**: `postgres` (без открытого порта наружу, пароль из `.env`), `meilisearch` (ключ из `.env`), `redis` (если 8.3 выбрал Redis),
  `web`, **Caddy** (сам получает https-сертификат Let's Encrypt для домена; `deploy/Caddyfile`). Тома: база, поиск, фото (`MEDIA_DIR`), `.data`
  (ключ шифрования, фиды), копии (`BACKUP_DIR`). Ограничение размера журналов Docker. Загрузка фида 60 МБ — лимит тела и в Caddy.
- При старте контейнера — `prisma migrate deploy` и ремонты `packages/db/prisma/repairs/` (как `scripts/update-site.ps1`); **сид не запускать**
  при каждом старте (он перезаписывает права ролей) — только первый раз, отдельной командой в инструкции.
- **`.env.production.example`** — все переменные сервера с пояснениями (`NODE_ENV=production`, `PUBLIC_URL`, `BOT_WEBHOOK=on`, пароли базы/поиска, `SECRETS_KEY`,
  `BACKUP_DIR`, `MEDIA_DIR`).
- **`deploy/update.sh`** (обновление на сервере одной командой: копия базы → `git pull` → сборка → перезапуск → проверка `/api/health`; при ошибке —
  откат на прошлый образ) и `deploy/README.md`.
- Требования к серверу для владельца (без выдуманных цен — «уточнить у хостинга»): Linux (Ubuntu 24.04), 2 ядра, 4 ГБ памяти, 60+ ГБ SSD (фото растут),
  расположение — Европа или Украина; вопрос владельцу — строка в `docs/QUESTIONS-TO-OWNER.md`.
- Проверка без сервера: `docker build` образа и `docker compose -f docker-compose.prod.yml up` на ПК/в облаке с адресом `localhost` (Caddy — с внутренним
  сертификатом), пройти e2e (`pnpm test:e2e` на этот адрес), Lighthouse на боевой сборке. Если Docker в сессии недоступен — собрать `standalone`
  и запустить `node server.js`, а сборку образа отметить в «не проверено».

### 8.5 Инструкция переезда и чек-лист запуска
Зачем: чтобы переезд с ПК на сервер прошёл по шагам без потерь, а перед открытием всё было проверено.
- **`docs/LAUNCH.md`** — пошагово, простым языком (Windows у владельца, Linux на сервере):
  1. Купить домен и сервер (что выбрать — из 8.4; регистратор и хостинг выбирает владелец). Запись DNS `A` → адрес сервера.
  2. Подготовить сервер: Docker, папка проекта, `.env` по `.env.production.example` (пароли — сгенерировать, никому не присылать).
  3. **Перенос данных с ПК**: копия базы (8.1, «Сделать копию сейчас»), папка фото, **ключ шифрования** → сервер → `pnpm backup:restore` → `search:reindex`.
     Во время переноса новые заказы на ПК не принимать (заранее выключить сайт на ПК).
  4. Запуск `docker compose -f docker-compose.prod.yml up -d`, проверка `/api/health`, вход владельца с кодом из приложения.
  5. Перенастроить внешние сервисы на домен: бот — вебхук (`BOT_WEBHOOK=on`), кнопка Mini App в BotFather, KeyCRM — адрес вебхука статусов,
     mono — `PUBLIC_URL`; старый прототип на том же боте выключить (иначе 409). «Проверить подключение» у всех ключей в «Интеграциях».
  6. Сторож (UptimeRobot или аналог) на `/api/health` → уведомление владельцу.
- **Чек-лист тестовых заказов** (`docs/LAUNCH-CHECKLIST.md`, галочки): заказ с каждым способом оплаты и доставки, «1 клік», «Передзвоніть мені»,
  заказ пришёл в KeyCRM и в Telegram менеджеру, смена статуса → сообщение покупателю, оплата 1–10 ₴ + возврат (если оплата картой включена),
  чек Checkbox, вход через Telegram и Mini App, остатки списались, тестовые заказы удалены/помечены. Браузеры: iPhone Safari, Android Chrome,
  внутри Telegram, Instagram, TikTok, компьютер (Chrome, Safari/Edge). Закрывает хвосты Х8, Х13 (обе строки), Х4.
- **Открытие для Google** — переключатель владельца в «Проверке перед запуском» (8.3), а не правка кода: `app/robots.ts` читает настройку;
  «открыто» = витрина разрешена, закрыты `/admin`, `/design`, `/api`, `/cart`, `/checkout`, `/order`, служебные сочетания фильтров. Карта сайта и мета — Этап 6
  (владелец решает: до открытия или после).
- **Откат**: если на сервере что-то не так в первые дни — как вернуть сайт на ПК владельца (копия с сервера → ПК), пошагово.
- Проверка: пройти `docs/LAUNCH.md` самому на «сервере» из 8.4 (локальный `docker compose`) от пустой машины до работающего сайта с перенесённой копией.

После 8.5 — **правки владельца** (`docs/QUESTIONS-TO-OWNER.md`), затем покупка домена и сервера и переезд по `docs/LAUNCH.md`.

## Допущения (в `docs/QUESTIONS-TO-OWNER.md`, владелец может поменять потом)
1. Уровни скидок — пороги прототипа 5 000 / 15 000 / 40 000 ₴, 0/3/5/10 %, по умолчанию **выключены**, включаются в админке.
2. Резерв: при заказе — резерв, при «Отправлен» — списание, при отмене — возврат.
3. Реферальная программа: ссылка и учёт приглашённых; размер бонуса — настройка, по умолчанию выключено.
4. SMS-вход: провайдер не выбран → заглушка.
5. KeyCRM: делаю подключение, выключено по умолчанию.
6. Mini App и вход через Telegram на сайте полностью проверяются только с доменом (https) — на Этапе 8.
7. Генерация описаний — нужен ключ ИИ-сервиса → заглушка.
