### Блок «Аналитика»: GA4, GTM, Google Ads, Meta Pixel, TikTok Pixel

**Устройство** (решение плана): сайт пишет события **только в `dataLayer`** в формате GA4 e-commerce (`event`, `ecommerce.items[]` с `item_id` = артикул,
`item_name`, `item_brand`, `item_category`…`item_category3`, `price`, `quantity`, `currency: "UAH"`, `value`); на страницу ставится **только контейнер GTM**,
а теги GA4, Google Ads (конверсия + ремаркетинг), Meta Pixel и TikTok Pixel живут внутри GTM. Готовый контейнер (теги, триггеры, переменные) — файл
`deploy/gtm-container.json`, владелец импортирует его в свой GTM («Админ → Импорт контейнера»). Новый рекламный кабинет потом — без программиста.

**События**:

| Событие | Когда | Данные |
|---|---|---|
| `view_item` | открыта карточка товара | товар, цена (как покупатель видит) |
| `view_item_list` / `select_item` (желательно, дёшево) | список раздела/задачи/поиска; клик по карточке | товары списка (первые N), `item_list_id` |
| `add_to_cart` | «В кошик» в карточке, в списке, «1 клік», повтор заказа | товар, количество, цена с учётом опта |
| `remove_from_cart` (желательно) | убрали из корзины | товар, количество |
| `begin_checkout` | открыто `/checkout` | вся корзина, сумма (`coupon` не передаём — промокодов нет, Д73) |
| `purchase` | страница «Дякуємо» `/order/<номер>` | `transaction_id` = HM-…, `value` (товары после скидок, без доставки), `shipping`, `items`, `coupon` |
| `search` | поиск (отправка формы и `/search?q=`) | `search_term` |
| `phone_click` | нажатие на `tel:` (шапка, подвал, «Контакти», «Дякуємо») | где нажали |
| `telegram_click` | ссылка на Telegram/бота/Viber (`messenger`: telegram/viber) | где нажали |
| `add_to_wishlist` | сердечко «Обране» (включили) | товар |
| ~~`coupon`~~ | **не делаем** — промокоды не нужны (Д73, 2026-10-05) | — |

**Правила**:
- **Покупка — один раз**: на «Дякуємо» событие только при первом показе — флаг в базе `Order.analyticsAt` (добавляющая миграция) ставится
  серверным действием при первой отправке; повторный показ/обновление — без события. `event_id` = номер заказа (общий с серверными событиями А3 — кабинеты
  не считают дважды).
- **Суммы — только с сервера**: данные для `purchase` и `begin_checkout` собирает сервер (`quoteCart`, заказ из базы), браузер их не считает.
- **Не засорять рекламу**: тестовые заказы (`is_test`), заказы из браузера с входом в админку, `Order.suspicious` — без `purchase` (ни в браузере, ни с сервера);
  в браузере с открытой админкой GTM не загружается вовсе.
- **Где не грузится**: `/admin`, `/design`, служебные адреса; на витрине — после показа страницы (`next/script` `afterInteractive` или `lazyOnload`);
  замер Lighthouse до/после (как в «Ловушках» CLAUDE.md), допустимая потеря — в пределах «плавания» ±8.
- **Mini App** — считается, параметр `channel: "miniapp"` (по `miniapp-bridge.tsx`).
- **UTM и метки кликов** (`utm_*`, `gclid`, `fbclid`, `ttclid`) — сохранять в куку при входе (`proxy.ts`, как `hm_ref`) и в заказ (`Order.utm` или поле
  в существующем JSON) — для отчётов «откуда заказы» и серверных событий А3.
- Чистая логика (собрать `items` из товара/корзины/заказа, решить «слать ли purchase») — `packages/core/src/shop/analytics.ts` + тесты;
  в браузер — без серверных модулей (как правило про `@handyman/core/shop`).
- **CSP**: `script-src` не задан (`lib/security-headers.ts`) — GTM и пиксели не блокируются; `Permissions-Policy: browsing-topics=()` оставить.

### 8.1 Резервные копии и проверка восстановления — **сделано** (2026-09-29, `docs/BACKUPS.md`, хвост Х17)
Зачем: на своём сервере сломанный диск или ошибка = потеря заказов, клиентов, остатков, ключей.
- **Что копируем**: база (`pg_dump -Fc`), папка фото `MEDIA_DIR`, **ключ шифрования** (`SECRETS_KEY` / `.data/secrets.key` — без него ключи
  «Интеграций» в копии не расшифровать). Поисковый индекс не копируем — пересобирается `pnpm search:reindex`. Фиды (`.data/feeds`) не нужны.
- **Когда**: каждый день в 03:30 из `runJobs` (как сводка 21:00), хранить 14 ежедневных + 8 еженедельных, старые удалять. Папка — `BACKUP_DIR`
  (новая переменная в `.env.example`; пусто — `.data/backups`). Фото — не целиком каждый день, а новые файлы (копия папки с пропуском уже скопированных).
- **Вторая копия вне сервера** (на случай, если умер весь сервер): выгрузка в S3-совместимое хранилище — поле в `INTEGRATIONS` («Резервные копии: адрес,
  ключ, корзина»); без ключа — только локально + предупреждение в «Резервных копиях». Какое хранилище — вопрос владельцу (Д-строка), допущение: любое S3-совместимое.
- **Проверка восстановления**: раз в неделю автоматически восстановить последнюю копию во временную базу `handyman_restore_check`, сверить число строк
  в главных таблицах (Product, Order, Client, StockMove …), удалить временную базу. Не получилось — тревога владельцу в Telegram (механизм тревог 4.8).
- **Админка «Резервные копии»** (`/admin/backups`, только владелец — `requireOwner()`): список копий (дата, размер, проверена ли), «Сделать копию сейчас»,
  «Скачать» (файл базы — только владельцу, запись в `AuditLog`), состояние второй копии. Модуль — `packages/db/src/backups.ts`, чистая логика
  (какие копии хранить, имена файлов) — `packages/core/src/backups.ts` с тестами.
- **Восстановление вручную**: `pnpm backup:restore <файл>` + раздел в `docs/BACKUPS.md` (пошагово для владельца и для сервера).
- Откуда `pg_dump`: на сервере — в боевом образе (8.4 ставит `postgresql16-client`); на ПК владельца — через `docker exec handyman-next-postgres-1 pg_dump`
  (путь к docker — как в `scripts/update-site.ps1`). Выбор способа — одна функция в `backups.ts`.
- Тесты: интеграционный — копия `handyman_test` → восстановление во временную базу → совпадают строки; core — правило хранения 14/8.

### 8.3 Защита: спам-заказы, вход в админку, безопасные настройки — **сделано** (2026-09-30, хвост Х19)
Зачем: чтобы боты не завалили менеджера фальшивыми заказами и никто не подобрал пароль.
- **Лимиты в базе, а не в памяти** (сейчас `tooMany()` в `app/[lang]/cart-actions.ts` — в памяти, сбрасывается при перезапуске): общий модуль

- **Проверка перед запуском** (`/admin/launch-check`, только владелец): список «готово / не готово» — сменён ли `ADMIN_TOKEN` и пароль `owner`, задан
